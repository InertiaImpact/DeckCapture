# Read-only Windows DeckLink inventory helper

In normal no-argument mode, `DeviceInventory.cpp` enumerates installed Desktop Video COM objects and reads the active profile attributes and selected video input connection. It has no capture/input-enable, profile activation, configuration setter or preference-write calls. The receiving machine needs Desktop Video; it needs neither the SDK nor a compiler. Normal .NET builds work without the optional helper.

Rebuild on a Windows developer machine with Blackmagic DeckLink SDK 16.0 and Strawberry GCC 13.2 / WIDL 8.5:

```powershell
./src/Capture/native/Build-DeviceInventory.ps1 `
  -SdkPath 'C:\SDKs\Blackmagic DeckLink SDK 16.0' `
  -BuildDirectory 'C:\Builds\DeckCapture-inventory-new' `
  -OutputDirectory 'C:\Packages\DeckCapture\media-tools'
```

Use a fresh nonexistent build directory. The script copies the main SDK IDLs and complete DirectShow `KsDeckLink.idl`, generates their headers/IID definitions with WIDL (never a hand-written interface vtable), applies the documented WIDL compatibility declaration only to the copy, retains Blackmagic's license on the generated header/IID source, statically links the compiler runtime and retains source/logs after success or failure. Keep this generated source/build support together with the media-tools compiler notices/source support. Package `DeckCapture.DeviceInventory.exe`, `NOTICE-DeviceInventory.txt`, and `device-inventory-provenance.json` in the release's `media-tools` directory. No generated SDK files or executable belong in Git. Inspect imports (`objdump -p`) when changing the compiler; non-Windows runtime DLLs must not become an undeclared deployment dependency.

For normal discovery the caller permits one helper process at a time, with a five-second total wait/process budget, 131,072 characters per output stream and Windows process-job containment. Missing helper, missing driver, timeout, invalid output and unmatched handles leave FFmpeg discovery usable with an inventory warning. FFmpeg's own discovery retains its separate twenty-second budget. Each refresh is a snapshot; external profile changes/hotplug require another refresh. DeviceGroupID groups only explicitly reported nonzero IDs. No label or enumeration order is used to infer physical identity.

Connector mapping lives in managed `DeckLinkModelCatalog.cs` and `DeckLinkInventory.cs`; adding diagrams or operator annotations does not require rebuilding this helper. The [official SDK §2.4.11 profile tables and illustrations](https://sdk-doc.blackmagicdesign.com/decklink-sdk/HighLevel/profiles.html) cover Duo 2, Quad 2 and 8K Pro (SDK 16 printed pp31–32). Legacy Duo/Quad layouts use vendor-authored historical manuals, with operator assertions rather than inferred native grouping; the full source/coverage matrix is in `docs/operations/INPUTS.md`. Other models use explicitly defined custom diagrams until primary evidence supports a registry addition.

Never decode opaque device handles or derive a group/model from endpoint order or a DeckLink SDI label: original Duo/Quad can expose that same model string. Unknown/zero group IDs remain unknown. `InputWiring.cs` retains operator wiring separately, cannot override a nonzero SDK group or verified connector evidence (an unknown group layout may receive a confined annotation retaining the SDK ID), and labels it `Operator`. Profile-assigned multi-BNC sets do not establish actual link mode. This helper supplies read-only driver metadata, not signal lock, cable validation or capture acceptance.

## PCI diagnostics

`PciInventory.cpp` adds a separate `pciInventory` report using read-only SetupAPI/Configuration Manager calls. It selects present PCI device nodes whose hardware IDs have the exact `PCI\VEN_BDBD` vendor field. Each node carries its reported instance/hardware IDs, service, description, bus/address, location paths/info, UI/slot number, container ID, raw physical-location bytes and at most eight ancestors. Absent/unsupported properties stay unknown; a missing UI number does not imply a slot number. The report is bounded to 64 nodes, 16 strings per list, 512 characters per string, 16 KiB per Windows property and 64 KiB JSON. `truncated` and `parentsTruncated` identify limit hits. Errors in these optional records do not invalidate an otherwise successful SDK or FFmpeg listing.

`topologicalId` and `deviceInterface` are exact SDK attributes, exposed separately from Windows evidence. The SDK documents topology IDs as OS-enumeration based and potentially affected by moving/reconnecting hardware. This code does not infer their bit layout, compare them to Windows PCI addresses, group endpoints by parent paths, or claim a slot-to-endpoint join. Windows PCI address decoding alone follows [Microsoft's documented device-high-word / function-low-word representation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-device_registry_property). Keep both the raw address and decoded values for review.

## Explicit idle-only identity mode

The separate fixed argument `--pcie-correlate-idle` supports the supervisor's `POST /api/inputs/pcie-probe` diagnostic. Normal no-argument discovery remains DirectShow-free. Only the idle command may enumerate video monikers and read their storage DevicePath, resolve that exact interface devnode through at most eight CM parents to its first PCI ancestor, require an exact Blackmagic hardware vendor ID there, then bind the corresponding filter to query `IKsDeckLink` identity getters. It does not add filters to a graph, connect pins, run streams, set formats/configuration or change profiles. Binding can access a device, so the supervisor must retain the same atomic idle hardware reservation that excludes preparation/format probes for the entire operation, including cancellation cleanup.

Primary interface evidence is SDK 16 `Win/DirectShow/include/KsDeckLink.idl`, `IKsDeckLink::GetPersistentID` / `GetTopologicalID`. The latter is explicitly intended to identify devices lacking PersistentID, but its equality with the main SDK attribute needs observed exact matching, not a decoded bit layout. The SDK DeviceList sample queries the main API topology attribute; no DirectShow sample supplies a complete Windows devnode join. [Microsoft moniker storage](https://learn.microsoft.com/en-us/windows/win32/directshow/selecting-a-capture-device) documents reading DevicePath without creating a filter, while [SetupAPI interface details](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/accessing-the-properties-of-installed-device-interface-classes) provide the interface-to-devnode step when that exact path resolves.

Raw `interfaceInstanceId`, `interfaceAncestorInstanceIds` (at most eight) and `interfaceAncestryTruncated` preserve the lookup evidence. `DECKLINK\AVSTREAM` virtual children can lead to a PCI device; never assume DevicePath names the PCI node directly. Stop at the first PCI ancestor and refuse a non-Blackmagic device rather than climbing higher. Cycles, missing IDs, missing PCI ancestors and truncated chains fail without binding. `PciAncestry.h` contains the finite read-only traversal; the build script runs synthetic ancestry fixtures.

The managed probe serializes callers with a semaphore and a 15-second total wait/process bound; existing output limits and Windows process containment apply. Native idle output budgets are 24,576 bytes for SDK records and 27,648 bytes for filter records, plus the bounded PCI report; the complete helper output cannot exceed 131,072 bytes. It returns raw SDK/PCI/filter evidence plus per-endpoint `ExactIdMatch`, `Unmatched`, `Ambiguous` or `Conflict`. Only unique nonzero exact IDs on a complete, available observation may match; contradictory identities or truncation prevent acceptance. Raw zero IDs remain diagnostic values, not match keys.

Keep correlation diagnostic-only, including successes. Duplicate IDs, conflicting paths, missing interfaces/properties and timeouts must remain explicit unknown/error results. A shared bridge or ContainerId does not prove a physical Duo card; slot labels remain optional. The operations input guide records the initial three-branch observation and the subsequent target result: all ten endpoints exactly matched (six by TopologicalId, four by PersistentId), with no automatic PCI-based grouping or legacy jack-order inference. This validates the observed identity path, not universal board recognition or capture acceptance. No native binary, target output or machine-specific mapping belongs in source control.

Normal inventory also queries IDeckLinkStatus getter-only observations: VideoInputSignalLocked, DetectedVideoInputMode and CurrentVideoInputMode, plus the SupportsInputFormatDetection profile attribute. Keep values nullable unless the specific getter returns S_OK, preserve HRESULTs and do not confuse detected with configured mode. This path must never query/enable/start an IDeckLinkInput capture interface. Status snapshots do not establish continuous per-frame validity.
