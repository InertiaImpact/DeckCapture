# Implementation contracts

The supervisor owns persistent state, API routes, configuration and integration. Capture and delivery components reference `DeckCapture.Domain`; do not duplicate or silently alter its types. Update all affected consumers, documentation and persistence/restart tests when changing a contract.

## Components

- `src/Capture` exposes `CaptureBackend : ICaptureBackend`. Its isolated worker executable lives under `src/CaptureWorker`. It owns one input, monitoring, bounded pre-roll, FFV1/PCM capture, metrics, preview, graceful finalization, and capability probing. Both project files target net10.0 and have no web dependency. The agent documents worker location resolution. Synthetic sources are genuine media, never placeholder files.
- `src/Delivery` exposes `FileDeliveryEngine : IFileDelivery` and `TransferWindowPolicy.IsWindowOpen(TransferSettings settings, string timeZone, DateTimeOffset utcNow)`. One engine instance is shared across transfers for aggregate throttling. Destination publication requires source and destination SHA-256 validation. The root supervises admission, concurrency, retries, and persistence.
- `src/Supervisor` hosts the live UI at `/` and a versioned-by-contract JSON API below `/api`. JSON is camelCase; enums are strings as declared. Authentication defaults to loopback, with a configured access token required for LAN binding. Same-origin checks apply to mutations; tokens never go in query strings.
- `src/Supervisor/wwwroot` is the actual browser client. The approved `docs/preview` simulation remains a design reference. Use semantic HTML, ordinary console styling, modules, and no remote runtime dependencies. Browser clients never own timers or fabricate live capture status.

## Browser API

All mutation requests use JSON and accept an `Idempotency-Key` header. Recording commands accept `{revision: number}` and return the current job. Conflict responses are HTTP 409 with `{error: string}`. Validation failures use HTTP 400. Secrets are never returned.

- `GET /api/state`: `{configuration, channels:[{configuration, job, metrics}], recordings:[], deliveries:[], alerts:[], notifications:[], system:{stateDirectory, cacheFreeBytes, reservedBytes, windowOpen, overrideUntil, captureCapabilities, version}}`.
- `GET /api/events`: server-sent `state` events containing the same snapshot; browser reconnects by reading state again.
- `POST /api/recordings/prepare`: `PrepareRecordingRequest` from Domain. Returns `RecordingJob`.

An accepted immediate-start prepare can appear as Prepared in state events while its prior monitor drains and the input opens. That intermediate state is not a second instruction to start. Browser request feedback is scoped to the submitting channel; other channels remain operable. Recording state from the supervisor is authoritative even if the original response has not arrived. Waiting plus an Opening input is still preparing, rather than ready for manual Start.

- `POST /api/recordings/{id}/start`, `/stop`, `/cancel`: body `{revision}`. Stop finalizes media; cancel applies to prepared/waiting jobs.
- `POST /api/recordings/{id}/extend`: `{revision, seconds}`.
- `POST /api/recordings/{id}/review`: `{revision}` releases a reviewed job to the delivery queue.
- `GET /api/channels/{id}/preview`: latest generated JPEG; 404 until available. This never opens another device.
- `POST /api/deliveries/{id}/override`: `{enabled}`; `/hold`: `{enabled}`; `/retry`: `{}`.
- `POST /api/transfers/override`: `{enabled, hours:12}`. Overrides use absolute UTC expiry.
- `GET /api/configuration`: exported `AppConfiguration`, no secrets. `POST /api/configuration/validate`: candidate configuration -> `{valid, errors:[]}`. `PUT /api/configuration`: validated candidate; active job snapshots remain immutable except experimental global disable.
- `GET /api/destinations/{id}/folders?relative=...`: `{relative, folders:[{name, relative}]}` under an approved root only.
- `GET /api/recordings/{id}/qc`: validation summary and recorded events.
- `POST /api/reports/preview`: `{kind}` -> `{subject, body}`. `POST /api/notifications/test`: explicitly queues a test message only if SMTP enabled.
- `GET /api/health`: minimal readiness response, does not leak settings or credentials.

The runtime configuration is `AppConfiguration` from `src/Domain/Models.cs`; `docs/settings.example.json` uses that runtime schema with illustrative paths that must be edited before import. The original proposal is retained as `docs/settings.design-example.json`. Default development paths stay under the application data directory and use synthetic sources and a local delivery destination. Optional `capture.offlineQcEnabled` runs native full-file QC before package sealing; no qcli/QCTools XML report is generated.

## SMTP settings and password boundary

`notifications.tlsMode` retains the existing values `Relay` (plain connection), `StartTls` (required STARTTLS upgrade), and `Tls` (implicit TLS). New disabled settings default to `Relay` on port 25 without inferred login. Browser mode changes may suggest 25, 587 and 465 respectively; a saved explicit/custom port must not be overwritten. Settings and their exact port/security choices persist through the normal configuration API and StateStore restart.

`notifications.authenticationEnabled` is a nullable boolean for compatibility. New clients send an explicit boolean. `false` skips SMTP AUTH even when a prior username or password remains stored. Explicit `true` requires a username and requests login independently of connection security, including an operator-selected plain internal relay. Missing/null preserves old username-based inference; the old guard against inferred plaintext login remains until the user saves an explicit choice. Previously saved TLS/port values are preserved. `credentialReference` remains a deprecated round-trip field and is not a password; the browser does not edit it. No usable password belongs in `AppConfiguration`, exported settings or job snapshots.

`GET /api/secrets/smtp` returns only `{secretConfigured:boolean,status:"Configured"|"Missing"|"Unavailable"}`. `Unavailable` means a retained protected file could not be read/decrypted; it exposes no secret or underlying key details. `POST /api/secrets/smtp` accepts `{action:"Keep"|"Replace"|"Clear",value?:string}` under the ordinary authentication, same-origin, JSON and idempotency rules. `Keep` has no value and leaves stored bytes unchanged; `Replace` takes a nonblank password up to 4,096 characters; `Clear` has no value and explicitly removes the stored password without changing login/settings choices. A legacy `{value}` request still means Replace. The response is `{saved:true,secretConfigured,status}` with no password readback. Blank browser password fields mean Keep, never an implicit clear. Configuration and password operations are separate; the interface must report failures and not claim a password was saved if its request failed.

Passwords retain the `DeckCapture.SMTP.v1` Data Protection purpose and protected local file format; Windows host key protection remains in effect. Reads/writes/status/clear operations share the secret-store lock, replacements are atomic, and known password values are redacted from retained notification error text. Selected TLS modes keep normal MailKit certificate validation. Outbox acceptance is saved before SMTP disconnect, so a QUIT error does not resend an accepted message. `Accepted` means the SMTP server accepted submission, not that delivery to every mailbox is proven. A test-mail request is an explicit separate action; changing or saving settings does not send a message.

Local fixture coverage uses 127.0.0.1 and never forwards mail: plain relay with no login and explicit login, stale saved usernames/passwords with no login, security/auth transport selection, protected password keep/replace/clear, and configuration/protection/StateStore restart round trips. Optional TLS socket fixtures use a pinned generated fixture certificate without changing machine trust; enable them with `DECKCAPTURE_SMTP_TLS_INTEGRATION=1` on a host that permits TLS credentials. The automation Windows context currently reports Schannel `0x8009030E` before handshake, so TLS socket success is not claimed from this environment. Security-mode mapping and auth independence remain covered without weakening production certificate checks.

The default media command names `ffmpeg`/`ffprobe` (also `.exe` on Windows) prefer a paired `media-tools` folder in the application release. The isolated `capture-worker` also checks its release parent's folder. Explicit configured executable paths retain precedence, and an incomplete bundle fails rather than mixing tool versions. Capture, device discovery and offline QC share this resolution. A bundle's DeckLink capability must be probed; its presence is not proof of working capture hardware.

## Input discovery and diagnostics

`GET /api/inputs/catalog` returns `{models:[{id,modelName,connectors:[{id,label,kind,direction}],sourceUrl,sourcePage,vendorVerified}]}`. The registry contains documented original Duo/Quad, Duo 2/Quad 2/8K Pro layouts and an unverified custom fallback; it is not exhaustive DeckLink recognition. Direction is `Input`, `Output` or `Bidirectional`; Reference cannot capture. The operations input guide records model-by-model sources and profile maps.

`GET /api/inputs/discover` returns `{available, deckLinkSupported, devices, error, cards, inventoryError, pciInventory}`. Each device retains exact FFmpeg `name` as the configuration/runtime key, optional `description`, nullable raw `inventory` and nullable `connection:{cardId,connectorIds:[],mappingSource}`. Inventory is `{deviceHandle,deviceGroupId,persistentId,modelName,displayName,subDeviceIndex,subDeviceCount,profileId,supportedVideoConnections,selectedVideoConnection,physicalConnectorId,topologicalId,deviceInterface}`. The older singular `physicalConnectorId` remains the Duo 2 compatibility field; use `connection.connectorIds` for general/multi-connector assignments. Missing metadata stays null/empty. IDs are hexadecimal strings and profile IDs are FourCCs. `topologicalId` retains the exact SDK value, including zero, rather than applying the nonzero group-ID rule; `deviceInterface` is the raw SDK enum integer. Neither field encodes a documented Windows device-node join.

`cards:[{id,modelName,modelId,label,mappingSource,connectorLayout:[{id,label,kind,direction}],inputs:[{deviceName,connectorId,present,applied}]}]` includes SDK groups and saved operator diagrams. `mappingSource` is `Sdk` or `Operator`; standalone operator card IDs are `operator:<saved id>`; an eligible annotation of an unknown SDK layout retains the SDK group ID. SDK groups require exact handle matches and a nonzero DeviceGroupID. Do not derive identity from model/display text, opaque handle structure or enumeration order. A legacy endpoint named DeckLink SDI does not identify its physical card model. Zero IDs cannot form a shared card group.

The optional Windows helper reads attributes/configuration without opening inputs or changing profiles. FFmpeg discovery has a 20-second bound plus a separate five-second SDK bound. Missing helper/driver preserves successful FFmpeg sources with `inventoryError`. Receiver dependencies are Desktop Video, not SDK/compiler. Refresh observes metadata; it never persists/remaps channel assignments.

`pciInventory` is nullable for compatibility with older/missing helpers. When present it is `{available,devices,truncated,error}`. Its present Blackmagic PCI nodes carry `{instanceId,description,friendlyName,manufacturer,service,hardwareIds,busNumber,address,deviceNumber,functionNumber,locationInfo,locationPaths,uiNumber,containerId,physicalDeviceLocation,parents,parentsTruncated}`; parent records have the same scalar/list properties without recursive parents. `physicalDeviceLocation` is uninterpreted hexadecimal Windows property bytes. Optional Windows properties remain null/empty. The report selects exact `PCI\VEN_BDBD` hardware vendor fields, with at most 64 nodes, eight ancestors per node, 16 strings per list and 512 characters per string. Optional PCI failure preserves successful SDK/FFmpeg discovery. This report is evidence only: no new card groups, channel assignments or connector maps are produced from it. Shared parent/container IDs and missing slot numbers cannot establish a physical board.

`POST /api/inputs/pcie-probe` is a separate fixed diagnostic command with no body parameters; send `{}` under the normal JSON, authentication, same-origin and idempotency rules. It accepts no executable, path, filter, device selector or custom arguments. It holds the input-hardware reservation used to exclude format probing/preparation, returns 409 for prepared/active/opening captures, another hardware probe, shutdown or maintenance, and releases the reservation after completion/failure/cancellation. State reads remain responsive while the helper runs. The fixed native `--pcie-correlate-idle` mode may bind an exact Blackmagic DirectShow capture filter to read identity getters only. It creates no graph, connects no pins, starts no streams and changes no settings or profiles. Ordinary GET discovery never invokes this mode or binds a filter. Its result is diagnostic-only; neither a successful match nor the observed PCI tree enables automatic grouping or remapping.

The idle probe returns `{available,error,truncated,sdkDevices,pciInventory,filters,endpoints}`. `sdkDevices` contains full SDK inventory records; `pciInventory` has the ordinary diagnostic shape. `filters:[{friendlyName,devicePath,interfaceInstanceId,interfaceAncestorInstanceIds,interfaceAncestryTruncated,pnpInstanceId,topologicalId,persistentId,error}]` retains observed DirectShow evidence. `interfaceInstanceId` is the registered interface devnode; `interfaceAncestorInstanceIds` records at most eight raw CM parent IDs. `pnpInstanceId` is the first PCI node reached from that exact interface. The interface devnode itself may be a virtual `DECKLINK\AVSTREAM` child rather than the PCI node. Binding requires that first PCI node to have an exact Blackmagic hardware vendor ID; reaching a foreign PCI node stops lookup instead of walking higher. Cycles, missing identities, no PCI ancestor or ancestry truncation prevent binding and accepted association. `endpoints:[{deviceHandle,topologicalId,persistentId,status,matchMethod,pnpInstanceId,matches}]` reports `status` as `ExactIdMatch`, `Unmatched`, `Ambiguous` or `Conflict`; `matchMethod` is `PersistentId`, `TopologicalId` or null, and `matches` contains candidate filter records. A unique nonzero exact ID is accepted only on a complete, available observation with no conflicting supplied identity; PersistentId is preferred when both methods agree. Truncation prevents accepting exact associations. Raw zero SDK IDs remain visible but are not eligible match keys. `available:true` means enumeration was available, not that every endpoint matched or capture works. The operation has a 15-second total semaphore-wait/process deadline, process containment/cancellation, 131,072-character stream bounds, at most 256 filter records, and bounded 512-character identity/path/error strings. Native idle reports additionally cap SDK JSON records at 24,576 bytes and filter records at 27,648 bytes; the optional PCI report stays below its 65,536-byte budget. Limit hits are explicit and cannot silently establish a unique match. No matching logic uses shared parents, inferred ID bitfields or name/order similarity.

Target validation on November 3, 2026 produced ten complete `ExactIdMatch` results: six legacy TopologicalId and four Duo 2 PersistentId matches. The operations guide records the exact handles and Windows branches. This diagnostic result does not alter the discovery `cards`/`connection` grouping policy or configuration, and it does not infer legacy connector order.

SDK connector assignments require supported/selected SDI and documented exact model/profile/subdevice evidence. Duo 2 and Quad 2 use `2dhd`/`1dfd`; 8K Pro uses its own `4dhd`/`2dfd`/`1dfd`/`1dhd` rules. Hardware subdevice count is not a profile-group size. Several 8K Pro input connectors can belong to one endpoint; that does not establish actual link mode or signal lock. Unknown combinations remain unmapped.

`AppConfiguration.inputWiring` defaults to `[]` and persists through the existing configuration API. Entries are `{id,label,modelId,inputs:[{deviceName,connectorId}],customConnectors:[{id,label,kind,direction}]}`. These are display-only operator assertions, never capture source replacements or driver writes. Validation bounds cards/connectors/mappings at 32 each, enforces exact endpoint uniqueness across cards, one mapping per input connector, and rejects reference/output bindings. Custom connectors require `modelId:"custom"`; known templates cannot be modified. SDK grouping/evidence wins conflicting annotations, which remain visible with `applied:false` and a warning. One operator diagram may augment an SDK group only if all present saved bindings report that same group, no other operator diagram claims it, and the entire group has neither a verified layout nor any SDK connector assignment. This preserves the SDK ID; mixed grouped/ungrouped or multiple-group bindings are rejected as a unit. Absent endpoint annotations remain saved with `present:false`; no replacement is inferred. Wiring changes affecting a prepared/active/opening endpoint return 409; unrelated idle wiring remains editable. Job configuration snapshots retain their original annotations.

Channel configuration is unchanged: save `sourceKind`, exact `deviceName`, `formatCode`, and the other existing channel fields through the configuration API. Duplicate DeckLink keys are rejected case-insensitively. Prepared/active/opening channels cannot be remapped or removed; job snapshots retain their earlier assignment. The browser preserves saved unavailable names and shows them as unknown instead of choosing another input. Clicking a row or focusing one of its fields highlights its exact assignment; selecting an endpoint highlights all matching rows, including invalid draft duplicates, without changing any assignment. Synthetic rows remain distinct from hardware inventory.

`POST /api/inputs/formats` accepts `{deviceName}`, rejects prepared/recording work, reserves hardware admission and drains monitor-only sessions before driver probing; recording preparation and automatic retries are excluded until it finishes. It requires the exact currently discovered name and returns reported modes, not a detected live signal format. See `operations/INPUTS.md` and the capture/native maintenance instructions for parsing, connector evidence and hardware acceptance.

`GET /api/diagnostics/status`, `POST /api/diagnostics/settings {enabled}`, `GET /api/diagnostics/logs` and `GET /api/diagnostics/bundle` expose the redacted, bounded development diagnostics service. They use the existing authenticated API boundary and no-store responses; request bodies, headers and query strings are never logged. Default Console/EventLog providers are replaced to keep all runtime log sinks under the same policy.

`POST /api/maintenance/drain {enabled}` obtains a ten-minute idle-only maintenance lease. A successful lease atomically blocks new capture and transfer admission and drains monitor-only sessions; prepared/recording work or active transfers reject the lease. It does not terminate recordings. `DECKCAPTURE_MAINTENANCE_START=1` starts in this mode. Only explicitly trusted local deployment/control tools should use this operator API.

## Signal observation and automatic input format

`ChannelConfiguration.formatCode` defaults to `auto` for new channels and omitted fields. Browser-created channels and the example configuration use the same default. Explicit saved manual codes remain valid and are not silently migrated; an operator request to switch existing channels is persisted through the normal configuration API. Auto means initial format detection on the one owned input, not profile activation or seamless source-format changes. A worker completion before readiness must reject preparation/monitor start with its sanitized reported cause; a generic process exit is only a fallback when no worker result exists.

CaptureMetrics.signalLocked is nullable: true/false is an actual supported observation, null is unknown/unavailable; DeckLink workers do not manufacture false from missing SDK access. inputSignalPresent is a separate nullable observation from owned-input FFmpeg DeckLink frame-flag messages (or synthetic true), with inputSignalStatusSource Unavailable, FfmpegDeckLinkFrameFlag or Synthetic. analysisAvailable and nullable analysisAgeSeconds report monotonic freshness of successful segment analysis. Automation requires analysis within five seconds, rejects explicit no-input/false lock, and permits unknown hardware lock when real analyzed content meets the confirmation rules. Worker-receipt age also prevents a frozen protocol from retaining fresh status. Existing clients must display null lock as unknown and must not interpret pipeline frame/drop counts as hardware lock/device counters.

DeckLink formatCode accepts auto (case-insensitive) as well as existing validated manual codes. Auto omits the input format_code option and delegates initial detection to FFmpeg/the driver; it does not select a different device or promise mid-recording format changes. No existing saved code is silently rewritten. The ordinary SDK inventory adds nullable supportsInputFormatDetection and status:{interfaceHResult,videoInputSignalLocked,videoInputSignalLockedHResult,detectedVideoInputMode,detectedVideoInputModeHResult,currentVideoInputMode,currentVideoInputModeHResult}. Status getters do not enable inputs or start streams. S_OK results alone populate values; unsupported/failed getters retain HRESULT and null, and older helpers have null status. A read-only status snapshot is not the worker’s continuous signal observation.

`capture.encoderThreads` is an integer 1–64 with compatibility default 2, applied only when preparing a new immutable job. CaptureMetrics adds sticky boolean inputBufferOverrun/outputFrameDuplication and nullable integrityWarning. These reflect observed owned-FFmpeg diagnostics (and positive output-duplication progress), not exact lost-packet totals or hardware device-loss counters. They remain independent of metrics.warning so a successful/failed segment analysis cannot erase capture integrity evidence. Supervisor job warnings and final review/hold decisions must include late shutdown diagnostics even when progress droppedFrames remains zero. Output fps_mode is passthrough; received timestamps remain authoritative.

## Synchronized live preview

Automatic monitor-only sessions always use unlimited duration. Explicit compatibility monitor API opens use `capture.monitoringTimeoutMinutes` (0 means unlimited, default; maximum 1440). Prepared/content-wait sessions continue using `maximumArmedMinutes`. Internal `CaptureOpenOptions.MonitorOnly` defaults false and is set only for explicit idle monitoring; preparation must never inherit it. Omitted new settings remain compatible with saved configurations and recording snapshots. These timeouts apply only before recording output begins and do not replace recording duration timers.

The optional capture.livePreviewEnabled setting defaults true for newly prepared jobs and is frozen in each capture snapshot. Metrics expose livePreviewAvailable/livePreviewError; these are capability/readiness observations, not fabricated video. The existing JPEG endpoint remains a fallback. Browser media uses authenticated GET /api/channels/{channelId}/live/{jobId}/index.m3u8 and generated sibling indexN.ts assets, verifying that the requested immutable job is the current owned session for that channel. No client selects a filesystem path. Asset names, size and read boundaries are restricted to the generated monitoring directory, with ordinary API authorization and no credential-bearing query strings. Playlists/segments are not directory listings or arbitrary spool access.

Proxy H.264/AAC and lossless FFV1/PCM derive from the same input. Rescaling/frame reduction/stereo conversion belong only to the proxy output. Its intentional processing must not inflate preservation drop/duplication observations. Browser players start muted and retain their media element across SSE updates; authorization headers apply to every HLS request. The player library is pinned and bundled locally with its license/provenance; no runtime CDN is required. Destroying playback never calls a capture-stop endpoint.

POST /api/channels/{id}/monitor/start and /monitor/stop accept {} under ordinary same-origin JSON/idempotency/authentication rules. Channel snapshots add monitoring:{id,state,source,startedAt,error}, with state Opening, Live or Failed and source Monitor or RecordingJob. An existing capture session is reused; Stop returns409 for a RecordingJob owner. Monitor-only sessions are ephemeral server-owned ICaptureSession instances, not fabricated RecordingJobs; their GUID forms the immutable live-media epoch. The JPEG and live-HLS routes resolve the exact job or monitor owner. Input-alias exclusion, opening reservations, shutdown and maintenance leases include monitors. Configuration edits may drain affected monitor-only sessions but never remap prepared/recording inputs. Maintenance suspends automatic admission and drains monitor-only sessions; prepared/active recordings still reject it. Prepare reserves the input before stopping/reopening its monitor. The hosted supervisor automatically starts/retries eligible configured channels independently of browsers. GETs, page loads and channel selection never directly open inputs.

The capture Overview is a client-only view over those same channel sessions and command routes. Opening it never starts workers; the supervisor owns automatic monitoring. Overview commands carry the card's channel/job identity and current revision; they must not resolve a recording target through the globally selected detail channel. Multiple browser players require per-channel/session/token ownership, exact same-origin media authorization, stable media nodes across state refreshes and bounded reconnect behavior. Only one preview may be audible, including changes through native media controls. View/tab changes, page hiding, token changes and replaced sessions dispose obsolete players and release browser resources without issuing capture-stop commands. Unavailable inputs show No input rather than raw worker diagnostics.

## Independent audio channel monitoring

`CaptureMetrics.audioChannelRmsDbfs` is an array of sampled RMS levels in dBFS for the first two original audio-stream channels. Empty means unavailable; mono supplies exactly one value. Never substitute the aggregate `audioRmsDbfs` for a missing channel, duplicate mono, or represent missing audio as silence. Genuine digital silence has a finite -100 dBFS floor. The existing aggregate and automation thresholds retain their previous meaning.

Each worker owns its SegmentMonitor and caches its bounded FFprobe channel-count observation. Measurement reads at most 250 ms of interleaved PCM from an already closed master segment, never a second device input. The values use the existing `analysisAvailable` and monotonic `analysisAgeSeconds` freshness contract. A browser must blank stale or unavailable values even if the last numbers remain in the snapshot. These are sampled RMS meters with approximately 1–2 seconds latency, not peak, clipping, loudness or preservation-quality measurements; preview mute does not affect them.

Public channel metrics follow the exact current monitoring owner and session ID. During monitor-to-prepared or completed-job-to-monitor handoff, a newly opening owner exposes unavailable defaults until its own worker supplies measurements. Never fall back to a closing monitor or terminal recording's levels, signal flags, frame counts or media path merely because its object has not finished disposal.

## Operator recording controls and observations

The capture screen shows a compact preview/audio pair and four operational readouts: detected input format, time, frames and reported pipeline drops. Detailed black/luma diagnostics, raw device keys and codec capability text are kept out of the operator workflow; their underlying capture/detection behavior is retained.

Setup identifies the channel in its header. Filename is the primary field; an empty filename receives focus when a new idle setup first mounts. Live state refreshes preserve the operator's focus and draft. Duration buttons select configured presets; Custom focuses the minutes field and is selected whenever that field is edited. Fractional minutes round once to whole seconds for the API (1 second through 12 hours). `defaultDurationMinutes` is optional/null for legacy first-preset behavior, otherwise it must name a configured preset. This setting persists and participates in export/import and the General advanced editor.

`PrepareRecordingRequest.startImmediately` defaults to false. True performs preparation followed by the normal revisioned Start inside one accepted server-owned operation. Combining it with `waitForContent:true` is rejected before admission. Request cancellation can stop admission but cannot cancel an already accepted start; its buffered JSON and durable idempotency receipt finish independently of a disconnected browser. The existing prepare/start APIs remain compatible. An ambiguous error is reconciled against current server state before another action: a retained Prepared job may offer Start/Cancel; a worker start that might already have written media must keep its failed state and original evidence.

`CaptureMetrics.recordingFrames` and `recordingMediaSeconds` are nullable outside recording and reset at the worker's actual Begin. They are sampled FFmpeg progress deltas excluding monitoring and pre-roll; their update granularity is about a second. A Recording state may precede the first metrics update, so the UI shows zero/pending rather than falling back to lifetime counters. Original `frames`, `mediaSeconds`, timestamps, dropped-frame evidence and finalized-file validation remain independent and unchanged.

`detectedVideoFormat` is a nullable observation of the original closed FFV1 master header from the owned input, using the existing bounded per-worker probe. It includes dimensions, rational frame rate and known field order; unknown components stay explicitly unknown. It is never inferred from the configured `auto` code or the resized browser proxy, and explicit input loss/dead encoder suppresses the live observation. This does not establish format stability or hardware lock.

## Background QC ownership

Physical input admission uses tracked input ownership independently of durable job activity. Successful mandatory validation and capture-session disposal precede Validating; that file no longer reserves the input. Validating remains active for maintenance, shutdown, reporting and disk reservations. Optional RecordingJob.qcProgress carries {phase,frames,processedSeconds,durationSeconds,updatedAt}; it is observed telemetry, never a completion decision, and does not increment command revision. Channel views select capture owners independently of older validating files. See operations/QC.md for stage semantics and restart limits.
