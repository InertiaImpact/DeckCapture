# Capture component operations

## Implemented boundary

`DeckCapture.Capture.CaptureBackend` implements the Domain capture interface. Every opened session launches a separate `DeckCapture.CaptureWorker` process and one continuous FFmpeg input. That input produces one-second, independently decodable FFV1 version 3 / 10-bit 4:2:2 / 48 kHz 24-bit PCM Matroska spool segments. Preview and meters read completed segments. They never reopen the live input. Synthetic test bars with a sine wave, and synthetic black with silence, are genuine encoded sources.

Capability probing checks the configured FFmpeg device listing and FFprobe. The current development bundle has DeckLink input support; an arbitrary winget FFmpeg installation may not. Synthetic availability does not establish DeckLink support. A working Blackmagic driver, compatible device and source format still require commissioning on the hardware PC.

Final validation fully decodes/counts frames using an explicit video slice-thread budget: one quarter of logical processors, clamped to 1–8 threads. This is separate from capture encoder threads and leaves CPU capacity for other captures. The retained 1080p59.94 failure exposed FFprobe's inherited single-thread decoder default; a five-second interval took 19.51 seconds with that default versus 4.05 seconds with eight slice threads, counting the same 300 video/audio frames. The correction preserves the full-file scan and existing format/count checks; it does not accept header or packet counts as a substitute. Finalization deadlines remain bounded and failed/partial media stays retained.

The DeckLink input explicitly requests `-audio_depth 32` before opening the device, then records the existing 48 kHz `pcm_s24le` output. This avoids FFmpeg's default 16-bit input capture followed by padding to a 24-bit output file. The input container width does not prove that the deck, converter, embedded SDI signal or driver supplies 24 valid source bits; source precision, channel order and conversion behavior still require hardware measurements. Synthetic lavfi sources do not receive this DeckLink-specific option.

Published packages may include `media-tools` beside the supervisor. Default `ffmpeg`/`ffprobe` tool names can resolve to those bundled executables, including when invoked by the isolated worker under `capture-worker`. Explicit configured executable paths remain overrides. A bundled DeckLink-enabled build supplies the input adapter; it does not replace the installed Blackmagic driver or establish hardware acceptance.

## Build and worker discovery

Build `src/CaptureWorker/DeckCapture.CaptureWorker.csproj` using .NET 10. No Capture component NuGet packages are required. The worker references Capture, which references Domain. The supervisor must deploy the **complete** worker build/publish output (including `.runtimeconfig.json`, `.deps.json` and dependent assemblies) under `capture-worker` beside its executable. Publishing only the worker DLL is insufficient. On Windows, discovery prefers `DeckCapture.CaptureWorker.exe` when `coreclr.dll` is present beside it; that self-contained worker launches directly without a machine `dotnet` command. Otherwise discovery retains the DLL/`dotnet` fallback. Development fallback searches ancestor `src/CaptureWorker/bin/Debug/net10.0` then `Release/net10.0` locations. `DECKCAPTURE_WORKER_PATH` retains precedence with an explicit DLL or executable path; selecting a DLL explicitly still requires `dotnet`. Configured FFmpeg and ffprobe paths are resolved by the operating system under the service identity.

`scripts/Publish-DeckCapture.ps1` remains framework-dependent by default. Adding `-SelfContained` publishes the supervisor and worker with their runtimes; `-Runtime` defaults to `win-x64` for that mode. The script explicitly publishes the complete worker into `capture-worker` and verifies both Windows apphosts and runtime files. RID-specific builds copy worker files from `bin/<configuration>/<target framework>/<RID>`. Keep the worker's runtime files beside its executable. Self-contained publishing removes the machine .NET runtime requirement; FFmpeg/ffprobe and actual capture hardware requirements remain separate.

Control uses redirected local stdin/stdout JSON lines. This is an inherited, private process handle, not a network endpoint. All child-process arguments use `ArgumentList`; generated concat manifests contain only worker-generated segment basenames. Paths containing spaces and apostrophes are supported. Windows child processes are contained in kill-on-close job objects. If containment cannot be established, process startup fails. Ordinary shutdown sends FFmpeg `q`, waits up to 15 seconds, then kills the process tree if necessary. Closing the supervisor's pipe also requests graceful stop. This does not replace durable supervisor restart reconciliation.

## Timing and monitoring limits

`BeginRecordingAsync(durationSeconds: D, preRollSeconds: P)` runs the duration timer for D seconds **after** accepting the trigger. Pre-roll is additional. `UpdateDurationAsync` increases that original post-trigger duration, up to 24 hours; it does not restart the timer. Worker timers use a monotonic clock. Browser lifetime does not own either timer. Manual stop finalizes what is available.

This is a segment-spool feasibility adapter, not a frame-accurate native capture implementation. It retains P available closed segments plus the current open segment. Consequently retained pre-roll is approximately P through P+1 seconds, limited by time already armed. With P=0, up to one current-segment second can still precede the trigger. FFmpeg progress plus monotonic interpolation estimates the open-segment fraction; this estimate is explicitly not hardware timecode. Buffered input/output can make the estimate differ from actual source-frame placement. Although the worker runs D seconds after the trigger, the final file cannot guarantee exactly D seconds of source content after that trigger. The final media cap is D plus that estimated available pre-roll, with up to 150 ms of packet boundary tolerance. Manual stop uses the monotonic stop-request instant for this cap, excluding extra media generated during graceful encoder shutdown. Encoder shutdown and segment scanning can take additional wall time. `timing.json` records closed pre-roll, its one-second uncertainty, the estimate, post-trigger elapsed time and measured final duration. Do not claim source-frame placement or exact trigger-to-frame alignment from these numbers.

Monitoring keeps only the latest update. It samples one reduced 64×36 full-range luma frame and 250 ms of downmixed PCM from a closed segment, normally about 1–2 seconds behind the input. It does not analyze every frame or every audio channel independently. Black ratio is the sampled fraction at luma ≤16/255; `IsBlack` uses a 0.98 ratio. RMS is computed from the sampled mono PCM, floored at −100 dBFS; downmixing can cancel out-of-phase audio. The retained 64-point luma diagnostic contains vertical column means. The operator capture screen does not present it as a waveform scope. Production detection thresholds need deck-specific calibration and continuous/per-channel analysis if acceptance requires it.

Synthetic signal lock means synthetic frames were successfully decoded. This FFmpeg adapter cannot prove DeckLink hardware signal lock, device-level frame loss, format stability or frozen-output detection; hardware metrics report nullable signalLocked (null when unknown), independently of nullable inputSignalPresent from explicit owned-FFmpeg DeckLink frame-flag loss/recovery reports. Unknown is not false and frame counts do not prove lock. A separate read-only SDK inventory status snapshot retains getter results and HRESULTs; it is not merged into the worker signal stream. The drop counter contains only FFmpeg's reported pipeline drops. A zero value is not proof of no hardware loss. Frame/media counters are FFmpeg source-output totals since the session opened, including armed monitoring; final `CaptureResult` frames/duration come from decoding/probing the finalized media. `ffprobe` checks Matroska, FFV1, pixel format, PCM codec, sample rate, channels, positive duration and decoded frame count. FFV1 v3 and slice CRC are explicit encoder settings; ffprobe does not independently expose the FFV1 version in this validator. Full preservation conformance, A/V synchronization and CRC acceptance remain commissioning work.

## Bounded resources and retained evidence

Armed pre-roll is limited to 0–60 seconds plus the current segment and at most one in-flight monitoring sample. Arming expires after the configured 1–240 minutes. The worker accepts at most 32 queued commands. FFV1 encoding uses two threads per channel and filter processing uses one thread; hardware throughput must be measured at these bounds. Monitoring files are replaced in place; FFmpeg's live segment index retains three entries. Original segment source-time intervals are recorded for concat, preventing container audio packet tails from accumulating duration drift. Error tails retain the latest 100 lines, and command-output collection is capped near 1 MB. Monitoring subprocesses time out after five seconds. Remux and full-frame ffprobe validation share a duration-scaled deadline: twice the requested recording duration plus five minutes, with a five-minute minimum and a one-day maximum. This allows approximately 0.5× realtime validation plus remux/startup overhead; it is a deadline allowance, not a throughput guarantee. A 60-minute job has 125 minutes and a 120-minute job has 245 minutes. A timeout retains the original spool and partial output for review.

Recording segments are retained until explicit retention action, on success as well as failure. Finalization writes a separate `.partial`, validates it, then moves it to the requested output without overwriting anything. Existing output or partial names are rejected. Spool plus final media can require approximately twice the recording size. Reserve that amount **and** pre-roll/emergency space before admission. Retained older jobs also consume disk; this component never silently deletes them. The worker only discards its own older armed-monitoring segments, before those segments belong to a recording.

The session also retains `worker-stdout.log` and `worker-stderr.log` in its working directory (normally `.spool/<jobId>`), above the individual `spool-*` media directory. Each keeps at most 200 lines of 2,048 characters. Persistence runs off the protocol reader, batches writes for one second and flushes on session disposal; it is best-effort on full/unavailable disks. stdout logs retain lifecycle/command/result events and at most one metrics update per 30 seconds. They omit media/preview paths and waveform arrays. Diagnostic error text redacts Windows paths and credential-style assignments. These are bounded troubleshooting tails, not complete media/audit histories; a hard process exit can lose the latest unflushed lines. Diagnostic exports may include these files through their fixed evidence allowlist. Review exports before sharing operational details.

## Failure recovery and maintenance responsibilities

On encoder exit, missing streams, dropped-frame reports, decode failure, timeout, full disk or interrupted finalization, do not publish the media as delivered. Preserve `spool-*`, `.partial`, `encoder.log`, `timing.json`, `concat.txt` and `validation.json` where present. The worker never restarts into the same recording filename. The supervisor must mark interrupted active jobs after restart and retain the originals. An operator may inspect and remux surviving closed segments into a **new** filename, validate every stream and review duration/A/V continuity. A final open segment may be truncated; do not discard the remaining valid segments because of it. There is no automatic recovery success claim or cleanup of undelivered media.

The capture maintainer owns FFmpeg argument/profile changes, process containment, source ownership, spool timing, sampled metrics and probe validation. The supervisor maintainer owns persistent job transitions, reservation/emergency-stop policy, duration admission/extension, immutable snapshots, restart reconciliation and retention approval. Changing segment size, frame cadence, audio layout, FFmpeg version, worker protocol or FFV1 options requires updating timing/capability documentation and rerunning synthetic and hardware acceptance.

## Verification

Run the normal component/solution build and test suite. Capture unit tests cover black/silence/RMS/waveform derivation and invalid resource bounds. Build CaptureWorker before enabling integration tests:

```powershell
$env:DECKCAPTURE_CAPTURE_INTEGRATION='1'
dotnet test tests/DeckCapture.Tests/DeckCapture.Tests.csproj --filter FullyQualifiedName~CaptureTests
```

These tests create unique media under `.local/capture-tests` and intentionally retain evidence. They require FFmpeg/ffprobe. They test five post-trigger seconds with pre-roll, preview, decoded frame count, correct codecs/audio, black/silence, extension and manual finalization. Synthetic evidence does not validate capture hardware.

Implementation verification on October 31, 2026: the worker built with zero warnings/errors and the four initial focused tests passed with integration enabled (zero skips). Sample D=5/P=1 outputs measured 6.080 s / 152 frames and 6.805 s / 170 frames, both FFV1 `yuv422p10le` plus stereo `pcm_s24le` at 48 kHz. This observed timing spread is evidence of the segment/progress limitation described above, not proof of frame-accurate capture. Existing-output bytes were preserved, previews had a valid JPEG signature, black/silence metrics matched their source, and extending then manually stopping produced validated media. An additional real-media regression subsequently passed at four offsets around the automatic deadline with four simultaneous stop callers each; every caller received the same authoritative completion result. Stop requests intentionally do not require a separate command acknowledgment while the worker is already finalizing. Test evidence from the isolated component run is retained under `.local/capture-component-evidence` in the development staging directory.

Before production: enumerate and pin actual device/subdevice/connector identity; test each requested mode and 10-bit path; confirm exact embedded audio order and depth; measure A/V sync and trigger/pre-roll interval against a visible timecode source; validate signal-loss/format-change detection; compare independent source and encoded frame counts; simulate encoder/worker/supervisor crashes and full disks; test simultaneous channels, storage pressure, preview load and transfer verification; verify destination/archive playback and FFV1 v3 conformance. DeckLink ancillary data, source timecode, captions, transport control, hardware lock and exact format-change handling are not implemented by this adapter.

## Duration controls

Choose a preset to fill the duration in seconds. Choosing Custom focuses the seconds field; typing a duration selects Custom. Values remain in the channel draft across live updates and channel switches. The setup card remains mounted while its channel, job state and setup configuration are unchanged; surrounding metrics continue updating. A channel/job-state or setup configuration change rebuilds it so locking and available controls reflect the server state. These are browser drafts until Prepare or Prepare & arm submits the duration; the supervisor still owns the timer.

## Automatic format and hardware signal observations

New channels and configurations with no format field default to Auto detect (`formatCode: "auto"`), which omits FFmpeg’s `-format_code` option on that owned input. FFmpeg then attempts initial hardware format detection; unsupported detection or an absent signal fails preparation explicitly. This does not promise seamless format changes during a recording. Existing explicit manual codes remain unchanged unless an operator selects Auto; Hi50 is 1080i50, while Hi59 is 1080i59.94. The format dropdown always offers Auto detect, including before a hardware format list has been loaded.

If monitoring cannot start, the worker's reported encoder failure must reach the operator rather than being replaced by an empty process-exit error. `Cannot Autodetect input stream or No signal` can mean a stopped/disconnected source, unsupported signal, or an inactive endpoint in the card profile. Auto detection does not enable inactive endpoints. On Duo 2 with the one-subdevice full-duplex profile (`1dfd`), indices 0/1 capture SDI 1/3; indices 2/3 are inactive and SDI 2/4 belong to the paired outputs. Four independent input connections require the two-subdevice half-duplex profile (`2dhd`) for the affected groups in Desktop Video Setup. Profile changes can interrupt other inputs; DeckCapture never changes profiles automatically. See the [vendor profile table](https://sdk-doc.blackmagicdesign.com/decklink-sdk/HighLevel/profiles.html).

Content starts and experimental end inference require recent successful closed-segment analysis (analysisAvailable and analysisAgeSeconds <= 5). Explicit loss/false lock blocks them; unknown hardware lock alone does not block actual analyzed picture content. Stale or unavailable analysis resets confirmation. Signal status and FFmpeg pipeline drop counts remain separate from device-level loss counters. The live bounded encoder.log is included in diagnostics while an input is open. A prepared/armed input that reaches MaximumArmedMinutes expires and requires a new Prepare; it does not silently become a manually startable job with a dead worker.

The browser keeps the preview card and displayed JPEG mounted during live metric refreshes, decodes the next image before swapping it, and allows at most one preview request per mounted image. Failed updates retain and label the last image as stale. Format auto-detection and input-presence reports are genuine driver/FFmpeg observations, not synthetic success.

## Capture throughput and integrity reports

`capture.encoderThreads` sets the per-input FFV1 encoder thread budget (1–64, compatibility default 2). It belongs to the immutable job capture snapshot. The hardware PC reports 40 logical processors; eight threads is a bounded single-input trial for the observed 1080p59.94 source, not a promise of multi-channel capacity. FFV1 codec version, pixel format, audio precision and default slice selection remain unchanged. Output uses `-fps_mode:v passthrough` to retain received frame timestamps instead of allowing automatic CFR duplication to conceal timing gaps.

An owned FFmpeg DeckLink input-buffer overrun is evidence of discarded packets. Output duplication is a separate integrity problem. Sticky inputBufferOverrun/outputFrameDuplication observations and integrityWarning are independent of the generic monitor warning and progress DroppedFrames. A zero progress drop counter does not clear these flags. Final job/delivery review must retain these observations, including messages arriving during shutdown; no clean Complete/delivery should be inferred from a valid container alone. A monitoring audio-sample failure must not be hidden or treated as silence. Larger input queues can absorb short stalls but cannot solve sustained slow encoding.

The first Auto test on November 3 detected Hp59 (1080p59.94), and SDK getters reported lock and current/detected Hp59. Its SDI color-bar preview was genuine, but the two-thread input logged overruns and output duplication. A copied one-second closed segment had 60 video packets and only seven sparse PCM packets (about 117 ms of actual audio), proving that the monitor warning reflected missing source data. That test never started a final recording. Keep its evidence; use a fresh input open when comparing a new thread budget.

Primary references: [FFmpeg codec threads](https://www.ffmpeg.org/ffmpeg-codecs.html#Codec-Options), [DeckLink queue semantics](https://www.ffmpeg.org/ffmpeg-devices.html#decklink), [frame timestamp passthrough](https://www.ffmpeg.org/ffmpeg-all.html#Advanced-options).

Eight-thread follow-up on the hardware PC: a fresh Auto preview ran beyond 95 seconds with no reported input buffer overrun or output duplication and fresh analysis. Its copied one-second segment contained 60 video packets and 60 PCM24 packets (48,048 samples, 1.001 seconds of audio). The hardware capture setting was saved as eight threads; Test1 remains Auto. No final recording was started. This is a single-input color-bar trial; final-file preservation and intended simultaneous workloads require separate acceptance. A local raw-input encode comparison also showed thread scaling (2 versus 8: 19.744 versus 7.353 seconds for the same ~10 seconds of frames), but that different machine is not the hardware-PC benchmark.

## Browser audio/video monitoring

A prepared or waiting input can provide synchronized H.264/AAC browser monitoring before Start recording. The existing FFmpeg input produces both the lossless master spool and a lower-resolution, reduced-frame-rate viewing stream with audio channels 1–2 (mono synthetic audio is duplicated to stereo). It never opens SDI twice. The proxy is for picture/sound checks; archival FFV1/PCM resolution, frame timing and configured audio channels remain unchanged. Browser playback is delayed and compressed, so it is not a substitute for master-file QC or frame-accurate synchronization checks.

Audio starts muted. Use the video player's native volume/mute and playback controls to enable sound or pause/resume viewing. These controls affect the browser only. Changing channels, leaving the capture tab or closing the browser releases the player without stopping the prepared input or recording. A new job uses a new media URL, so an old player cannot read reused segment numbers from a new session.

The rolling HLS files are bounded disposable monitoring derivatives under the owned spool, separate from retained source segments. A synthetic encoder preflight occurs before opening SDI; unavailable codecs or disabled livePreviewEnabled leave the JPEG fallback with an explicit explanation. Windows software Media Foundation H.264 and native AAC avoid requiring a separate GPL codec library in the private media build. Preview muxer I/O uses a bounded FIFO with loss/recovery permitted only for this disposable proxy. The encoders still share a process: a fatal encoder/process fault can end capture, and must preserve/report the partial master rather than restart or claim success. Station workload testing must include live preview overhead.

## Automatic input monitoring and thumbnails

The supervisor automatically monitors every configured channel. No filename, operator metadata or browser action is needed. A signal starts preview/thumbnails; unavailable inputs show No input and are retried periodically. Opens are staggered and retries are bounded to avoid a tight failure loop. No recording job is created by monitoring. Auto format detection needs an actual supported incoming signal and cannot enable inactive card-profile endpoints.

Automatic monitoring has no duration limit. Prepared/content-wait sessions keep their separate `capture.maximumArmedMinutes` limit (15 minutes by default); recording timers are independent. The compatibility `capture.monitoringTimeoutMinutes` field still applies to explicit monitor API opens, but automatic sessions use unlimited duration. Rolling buffers remain bounded, although each active channel consumes CPU and disk bandwidth. Simultaneous station capacity still requires hardware acceptance.

Prepared/waiting/recording sessions own their input exclusively. Prepare closes/reopens that channel's monitor with an immutable recording snapshot; this can introduce a short preview gap. Automatic retries never stop, reopen or restart a recording. After a recording or prepared job releases its input, automatic monitoring resumes. Configuration changes can retire affected monitor-only sessions; prepared/recording assignments remain protected. Maintenance reserves admission first, drains monitor-only inputs and suspends retries, while active/prepared recordings reject maintenance. Browser navigation and playback controls never stop workers.

## Channel overview

Use Overview above the Capture channels list to view all configured channels together. Each card uses the live stream of its existing monitored, prepared or recording session; unavailable inputs show No input while the supervisor retries. Open channel returns to its detailed recording setup. Recording controls below each card apply to that card's job, including its revision, rather than whichever channel was previously selected.

Overview previews start muted. The video player's native volume control selects its audio; enabling another channel's audio automatically mutes the previous one. Pausing a preview, switching views or leaving the page affects browser playback only; recordings and monitor-only inputs continue on the supervisor. Preview streams remain compressed and delayed, and do not establish preservation-master quality or tested multi-card capture capacity.

## Audio channel meters

The selected channel's main preview includes separate vertical Audio 1 and Audio 2 meters. These show sampled RMS in dBFS from the original source channels, whether preview audio is muted or enabled. Updates arrive with the segment analysis, normally about 1–2 seconds behind the input. Mono has no second-channel reading; unavailable or stale analysis has no numeric reading. These meters help check routing and approximate levels; they do not show instantaneous peaks, true peaks, clipping or loudness compliance.

## Windows MF/DeckLink shutdown regression

The pilot's FFmpeg 9.0.2 bundle needs the recorded MF COM ownership patch when using H.264 MF preview with DeckLink capture. The unpatched helper can initialize COM on an encoder-opening thread and uninitialize the main thread during output cleanup, before closing its DeckLink input. This can unload the driver behind a live input interface and cause a Windows access violation on StopStreams. Failed initialization and repeated cleanup must not uninitialize COM either. Preserve the patch and its ownership regression harness when replacing the paired media tools; inspect the bundle's `sourcePatches` provenance and retained source/test reports.

The mitigation balances successful MF startup/shutdown, tracks successful COM initialization and its thread, and skips foreign-thread COM uninitialization. A deferred owner-thread COM reference is bounded by DeckCapture's isolated FFmpeg process; this is not a general repair for repeatedly reopening encoders inside one long-lived process. Microsoft documents the required per-thread balance in [CoUninitialize](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-couninitialize). Synthetic ownership and media tests do not replace target-hardware shutdown testing. Never turn a native nonzero exit into successful finalization; retain the original segments and report the decimal/hex exit code.
