# Discovering capture inputs

Each channel has one Source list containing discovered DeckLink inputs, Synthetic · Test pattern, Synthetic · Black, and a manual input-name fallback. Choosing a source updates the existing sourceKind/deviceName/syntheticPattern fields; UI-only selection keys are never persisted. Switching to synthetic clears the physical highlight and hides hardware format controls; saved device names and formats remain available when switching back. Choosing manual input opens Details.

`GET /api/inputs/discover` returns `{available, deckLinkSupported, devices, error, cards, inventoryError, pciInventory}`. Devices retain exact FFmpeg `name` plus display-only `description` and optional SDK `inventory`. Configured channel labels and synthetic sources are never presented as detected hardware. Use `name` unchanged as `deviceName`; it is not a list index or bracketed human description. Saved assignments survive discovery reordering, missing devices and restart. Discovery never chooses a replacement input or changes configuration.

Discovery first checks `ffmpeg -devices`, then runs `ffmpeg -sources decklink` only if DeckLink input is compiled in. This first check matters: FFmpeg can silently exit successfully from `-sources decklink` when that input device is absent. Missing support yields `available:false`, `deckLinkSupported:false`, no devices and an explanatory error. An accessible build with DeckLink support can still fail driver/card/service-account enumeration; that yields `available:false`, `deckLinkSupported:true` and the bounded diagnostic error. A recognized successful listing with no inputs yields `available:true`, `deckLinkSupported:true`, an empty device list and an explicit no-devices message. None of these outcomes simulates success or establishes that an SDI signal is locked.

Source listing enumerates the SDK's input devices and does not start a capture stream. It may run while capture is active. It does not change channel mappings, start tape transport or choose a card profile. Devices configured as output-only might not appear among inputs. Discovery is a current observation under the application's service identity; hotplug, driver configuration, permissions and device profiles can change it.

## Physical inventory and compact rows

The optional bundled Windows helper `media-tools/DeckCapture.DeviceInventory.exe` reads device attributes and selected/supported video connections. It never opens an input or sets configuration/profile state. Desktop Video must be installed; the hardware PC does not need SDK headers or a compiler. Missing helper/driver, unsupported fields or unmatched handles produce `inventoryError` and explicit unknowns while preserving successful FFmpeg discovery.

Metadata joins only on the exact device handle. Nonzero SDK DeviceGroupID identifies a card group; 64-bit IDs remain hexadecimal strings. Zero, absent or duplicate identifiers are not a basis for grouping. `inventory` reports model/display names, persistent/group IDs, subdevice index/total, profile FourCC, connection names and a nullable physical connector. `cards` supplies SDK groups plus separately labeled operator diagrams, including custom layouts. See [the contract](../architecture/CONTRACTS.md#input-discovery-and-diagnostics) for all field names.

## Windows PCI diagnostics and idle identity probe

Normal input discovery adds optional `pciInventory` from read-only Windows SetupAPI/Configuration Manager enumeration. It reports present Blackmagic PCI nodes, their exact instance/hardware IDs, parent chains, raw/decoded Windows PCI address, location paths/info, optional UI/slot number, container ID and raw physical-location bytes. SDK `inventory.topologicalId` and `deviceInterface` are separate driver attributes. A missing helper/unsupported property remains unknown; an optional PCI error does not discard working FFmpeg inputs or SDK metadata. Limits and field names are in [the contract](../architecture/CONTRACTS.md#input-discovery-and-diagnostics).

These fields do not automatically identify original Duo cards. Do not decode SDK handle/topology strings as PCI bus/device/function values, pair endpoints by enumeration order, or group cards by common parent or ContainerId. Windows can propagate one container ID across non-removable descendants. Location paths describe the observed tree, and slot numbers are optional; absence never means slot zero or the next available slot. Only Windows' documented PCI address representation is decoded, independently of SDK identity. [SDK attribute semantics](https://sdk-doc.blackmagicdesign.com/decklink-sdk/DeckLinkAPI/enums/bmddecklinkattributeid.html), [Microsoft PCI addresses](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-device_registry_property), [container inheritance](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/how-container-ids-are-generated-from-the-removable-device-capability).

For explicit identity investigation, `POST /api/inputs/pcie-probe` accepts `{}` with the ordinary command security/idempotency headers. Close all prepared/active captures first. The supervisor atomically reserves hardware probing so another prepare/format/probe cannot enter; it refuses shutdown/maintenance and releases the reservation on every exit. It does not cancel jobs to make the probe possible. Unlike ordinary GET discovery, this fixed diagnostic resolves each registered interface through at most eight CM parents to its first PCI ancestor, verifies the exact Blackmagic hardware vendor ID, then may bind that DirectShow filter to call identity getters. Virtual `DECKLINK\AVSTREAM` interface devnodes are expected possibilities, not PCI IDs themselves. Lookup stops at the first PCI node and rejects foreign PCI hardware rather than searching above it. Raw interface/ancestor IDs and an ancestry-truncation flag are retained; cycles, missing identities or an unresolved/truncated chain prevent binding. It never adds a filter to a graph, connects pins, starts streams or changes settings/profiles. No request can select an arbitrary command, path or filter. The results remain diagnostic evidence, with ambiguous/unsupported identity left unresolved; automatic PCI-based grouping is disabled.

The probe result contains raw SDK/PCI/filter evidence and per-endpoint `ExactIdMatch`, `Unmatched`, `Ambiguous` or `Conflict` status. Only a unique nonzero exact PersistentId or TopologicalId with no contradictory identity on a complete observation can be accepted. A reported zero ID is retained as evidence but is not a matching key. Truncation prevents exact associations, and a successful enumeration can still leave every endpoint unmatched. A 15-second total wait/process deadline and bounded output apply. Even `ExactIdMatch` identifies an endpoint's Windows node, not a physical card model, signal lock, jack order or permission to enable automatic grouping. See the contract for exact fields.

## Diagram coverage and evidence

`GET /api/inputs/catalog` returns the explicit model registry. This is documented layout coverage, not a claim that every DeckLink model is automatically recognized or capture-tested. Top-to-bottom means the vendor drawing with the bracket retaining tab at the top. `Reference` is always a reference input, never a capture endpoint.

| Registry model | Top-to-bottom diagram | Assignment authority | Primary evidence |
|---|---|---|---|
| `decklink-duo-original` | SDI 2 output, SDI 2 input, SDI 1 output, SDI 1 input, Reference | Operator-confirmed exact endpoint only | Blackmagic April 2011 DeckLink Series manual, printed p57 |
| `decklink-quad-original` | Output/input pairs for SDI 4, 3, 2, 1, then Reference | Operator-confirmed exact endpoint only | Same manual, printed p59 |
| `decklink-duo-2` | SDI 4, 3, 2, 1, Reference | SDK model/profile/index/SDI evidence and nonzero card group; otherwise eligible operator assertion | SDK 16 §2.4.11, printed p32 |
| `decklink-quad-2` | SDI 8 through 1, Reference | Same SDK evidence requirements | SDK 16 §2.4.11, printed p32 |
| `decklink-8k-pro` | SDI 4, 3, 2, 1, Reference | Same requirements; one endpoint can own several profile-assigned input connectors | SDK 16 §2.4.11, printed p31 |
| `custom` | Operator-defined ordered connectors, kinds and directions | Operator assertion only; `vendorVerified:false` | Site's verified wiring record |

The [vendor-authored April 2011 manual](https://www.artisantg.com/info/Blackmagic_Design_DeckLink_HDPro_PCIe_Manual_2021310104551.pdf) is hosted by a third-party mirror; its authorship is Blackmagic, not the mirror. The original Duo diagram was also visually checked against Blackmagic's [October 2012 Desktop Video manual, p53](https://www.dve-x.com/fileadmin/user_upload/produkte/Blackmagic/PDFs/Decklink/Desktop_Video_Manual_October_2012.pdf). Current profile tables and illustrations are available in the [official SDK documentation](https://sdk-doc.blackmagicdesign.com/decklink-sdk/HighLevel/profiles.html). SDI, Mini Recorder/Monitor, Studio, Extreme, IP, newer revisions and other models have no verified built-in template in this registry; use a custom diagram checked against the exact model's vendor documentation. Similar names are not interchangeable models.

For Duo 2, `2dhd` indices 0/1/2/3 map to SDI 1/3/2/4; `1dfd` indices 0/1 map to SDI 1/3. Quad 2 `2dhd` indices 0–7 map to 1/3/5/7/2/4/6/8; `1dfd` indices 0–3 map to 1/3/5/7. 8K Pro `4dhd` maps 0–3 to 1/3/2/4; `2dfd` maps 0/1 to 1/3; `1dfd` index 0 owns input connectors 1 and 2; `1dhd` index 0 owns 1–4. These are profile-assigned connector sets, not measured signal routes or a detected single/dual/quad-link mode. Selected and supported connection must be SDI. Out-of-range indices and unknown model/profile/connection stay unmapped. NumberOfSubDevices is the hardware total, not a profile-group size.

## Operator wiring and unknown hardware

Save display-only physical annotations through configuration `inputWiring`: each card has `id`, `label`, `modelId`, `inputs:[{deviceName,connectorId}]` and `customConnectors:[{id,label,kind,direction}]`. Existing configuration defaults to an empty list. Select a documented model or define a custom ordered layout, then associate each verified input jack with its exact FFmpeg endpoint. These annotations do not change a channel's capture key, configure hardware, activate profiles or establish signal lock. They persist through normal configuration save/export/import and restart.

The server permits at most 32 cards, 32 connectors and 32 mappings per card; endpoint keys are unique across cards and input connectors are unique per card. Output/reference jacks cannot receive input mappings. SDK grouping and connector evidence take precedence: a conflicting operator entry is retained but not applied, with a warning. An unknown SDK group with no verified layout or connector assignments may receive one operator diagram only when every present saved binding belongs to that same group and no second diagram claims it. The effective card ID remains the SDK group ID. Mixed grouped/ungrouped endpoints or multiple groups are refused together; absent entries remain unapplied annotations. Discovery exposes `connection.mappingSource` and card `mappingSource` as `Sdk` or `Operator`; `present:false` retains a missing endpoint and `applied:false` identifies an annotation not used for highlighting. Missing devices are never replaced by a similar name or array neighbor.

Legacy Duo and Quad can expose several endpoints described as **DeckLink SDI**. That model string does not establish whether an endpoint belongs to a standalone SDI, Duo, Quad, or which physical card it belongs to. Opaque handle text, suffixes, consecutive enumeration order and zero/missing group IDs are not topology. Verify cabling under the site's idle commissioning procedure before saving operator wiring. Refresh after external profile/hotplug changes and review retained annotations; no refresh automatically rewrites them. A prepared/active/opening endpoint's wiring cannot be changed; unrelated idle annotations remain editable.

Compact rows retain saved configuration order. Clicking a row or focusing its fields highlights the row's exact assignment; selecting an endpoint highlights every matching row without changing it. Editing an input choice updates draft highlighting; only validation and save persist it. Duplicate DeckLink assignments are visible but rejected by the server. Saved unavailable/manual names stay visible rather than silently changing to a discovered or synthetic input. Prepared/active/opening channels cannot be remapped or removed, including while canceled input-open cleanup is still draining. Refresh after hotplug or external profile changes; SDK inventory is a snapshot; only explicitly saved operator annotations persist.

## Explicit format enumeration

`POST /api/inputs/formats` accepts `{deviceName}` and returns `{available, deckLinkSupported, deviceName, modes:[{code,label}], error}`. This action is explicit because FFmpeg's DeckLink format path obtains input interfaces and may select input connections. The supervisor rejects it with HTTP 409 while any capture is prepared, waiting, opening, recording, finalizing or validating, or while another format query holds the discovery reservation. The same reservation prevents preparing a new capture until the query exits. It does not hold the supervisor's state gate while waiting for FFmpeg, so timers/state snapshots remain responsive. Closing a browser cancels the query, not an accepted recording.

The query refreshes source discovery and requires the exact device identifier to still be present. Unknown or invalid identifiers cannot reach an input-open command. It then runs `ffmpeg -f decklink -list_formats 1 -i <deviceName>`, with each item as a separate process argument. No shell is involved. Names containing spaces, quotes or strings resembling flags remain one argument. No format query is performed automatically by the ordinary source-discovery endpoint.

`code` is FFmpeg's FourCC, such as `ntsc`, `Hi50` or `pal`. The padded FourCC `pal ` is returned as `pal`, which FFmpeg accepts. `label` preserves the reported dimensions, rational frame rate and field-order text; the application does not reinterpret 29.97 frames/s as 59.94 frames/s. A parsed table can be successful even if FFmpeg exits nonzero, because format-listing intentionally exits the input-open path. The parser requires the table header and recognizable mode rows and rejects known hardware failures. A format table is not a successful capture, current detected signal mode, connector validation or proof that every listed mode works with the configured 10-bit input path.

## Resource bounds, parsing and failures

FFmpeg capability/source/format discovery has a 20-second deadline. Optional SDK enrichment has a separate five-second deadline, so a source refresh can take up to about 25 seconds. Caller cancellation propagates. Timeout/process failures produce structured errors with no invented devices or modes; optional inventory failure preserves FFmpeg devices. stdout and stderr are drained concurrently; each is limited to 131,072 characters. Oversized output fails rather than silently returning a partial inventory. Errors expose at most 1,800 diagnostic characters. Source/mode lists are limited to 256 devices and 512 modes. Windows children use kill-on-close process containment, and cancellation or parsing/output failure terminates and awaits the process tree.

Parsing follows FFmpeg's source-list table: input identifier, bracketed description and parenthesized media types. Descriptions may contain balanced nested brackets; identifiers are preserved with case, spaces and apostrophes. Duplicate identifiers are collapsed using ordinal comparison. Other device-family sections and headerless text are ignored. Format parsing preserves valid three/four-character mode codes and the reported mode label. FFmpeg emits plain text rather than a structured discovery API: malformed, ambiguous/unbalanced text or an incompatible new output version must be investigated. The implementation does not infer missing inputs or modes from familiar card names.

An ordinary FFmpeg build may lack DeckLink support; check the selected executable rather than assuming capability from its filename. Synthetic capture remains a separate development source and is not shown as a detected card. Use a DeckLink-enabled FFmpeg build compiled against the appropriate SDK and validate the actual driver/card configuration before expecting inputs. This work does not install drivers, reconfigure hardware, stop other applications or start real deck transport.

## Maintenance and acceptance

`Capture/InputDiscovery.cs` owns process execution, capability/source/mode parsing and bounded results. `Supervisor/CaptureSupervisor.Discovery.cs` owns the global format reservation; `PrepareAsync` must continue checking that reservation under the same state gate. Route wiring, authentication and command policy belong to `Program.cs`. Keep the discovery runner's test substitution internal; no HTTP request may supply an executable path or arbitrary process arguments.

`Capture/DeckLinkInventory.cs` owns metadata parsing and exact-handle enrichment; `DeckLinkModelCatalog.cs` owns verified diagrams/profile maps; `InputWiring.cs` applies explicit operator annotations without rewriting SDK evidence. Native source/build instructions are `src/Capture/native/DeviceInventory.cpp` and `Build-DeviceInventory.ps1`; the SDK/compiler are development dependencies only. Any new model/profile mapping needs primary SDK/manual evidence and hardware validation. Do not make discovery writes or derive topology from names/order to fill an unknown field.

`DiscoveryTests` exercise official output grammar, nested descriptions, exact identifiers, PAL padding/field order, missing build support, empty/failed driver enumeration, a nonzero format-list exit, argument boundaries, stale identifiers, cancellation, and capture/format exclusion without blocking state snapshots. The optional installed-FFmpeg check runs source enumeration only; it never invokes real format discovery. Enable it with the existing `DECKCAPTURE_CAPTURE_INTEGRATION=1` test switch.

Verification on November 2, 2026: all 11 focused discovery cases passed with the installed-FFmpeg check enabled. The installed build truthfully reported no DeckLink support. Hardware/source/format success cases used explicit test doubles and published output grammar; they are not hardware acceptance. No real format query, input capture, driver change or action against the existing application was performed during these tests.

Primary references: [FFmpeg DeckLink input documentation](https://ffmpeg.org/ffmpeg-devices.html#decklink), [FFmpeg source-list output implementation](https://github.com/FFmpeg/FFmpeg/blob/n7.1.1/fftools/opt_common.c), and [DeckLink enumeration/format implementation](https://github.com/FFmpeg/FFmpeg/blob/master/libavdevice/decklink_common.cpp). Verify parser compatibility when upgrading FFmpeg. Actual acceptance still requires device/subdevice/connector inventory, each desired mode, source timing and SDI lock, audio order/depth, concurrent-channel throughput and driver/profile behavior on the target workstation.

## Read-only input status snapshots

Ordinary inventory now includes nullable supportsInputFormatDetection and an optional status object read through IDeckLinkStatus only. It queries the reported input lock, detected input mode and currently configured input mode separately; it never enables input or starts a stream. Each getter retains its HRESULT, and failed or unsupported values remain null. These are driver status snapshots at Refresh inputs, not continuous worker counters or proof that an inactive input can currently capture the cable signal. Unknown mode/lock remains unknown. The SDK DeviceStatus example uses this getter-only interface.

Hardware investigation on November 3, 2026: Test1 selected exact endpoint 81:d016aa50:00000000, model DeckLink Duo 2, subdevice0, SDI selected, profile1dfd. Its documented input is SDI1 (SDI2 is the paired output); the other active input is index1/SDI3. The retained original test used Hi50 and its owned FFmpeg log explicitly reported No input signal detected. This established the selected connector and the failure report, not the actual source format or physical cable continuity. Use Auto detect for a subsequent supported input open or a known correct manual code. Do not open another capture process or change profiles to investigate an already-owned input.

The subsequent Auto preview successfully reported supportsInputFormatDetection=true, SDK input lock=true and both detected/current input mode Hp59 (1080p59.94), replacing the old configured Hi50 mode. This confirmed the SDK SDI1 selection and incoming format. It did not establish reliable preservation throughput: the first two-thread session had real input queue overruns and sparse audio. See the capture throughput section before interpreting a good preview as a successful recording.

Automatic monitoring pauses for explicit idle-only format/PCI identity probes. The supervisor reserves hardware first, drains monitor-only sessions, runs the bounded probe and releases the reservation so previews resume. Prepared or recording jobs still reject these probes; ordinary input discovery remains read-only and does not drain previews.
